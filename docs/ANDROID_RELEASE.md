# Выкладка Android без ручной загрузки

CI сам отправляет подписанный AAB в Google Play — так же, как iOS-билд уходит в TestFlight. Все три
приложения одинаково: джобы `android-release` (Dhamma.Gift), `dict-release` (словарь) и
`uposatha-release` (Uposatha) в `.github/workflows/build-app.yml` вызывают один и тот же
`.github/workflows/play-release.yml`.

Пока нет секрета `PLAY_SERVICE_ACCOUNT_JSON`, джоба **ничего не делает и честно пишет об этом**
в сводке рана: зелёная галочка без загрузки — худшее, что может случиться с релизным пайплайном.

## Что настроить один раз (это может сделать только владелец аккаунта)

Сервисный аккаунт целиком делается в Google Cloud; Play Console узнаёт о нём только через
«Пользователи и разрешения». Страницы «Доступ к API» и связывания проекта в консоли искать не
надо — их там нет, и они больше не нужны: *«You no longer need to link your developer account to
a Google Cloud Project in order to access the Google Play Developer API»*
(developers.google.com/android-publisher/getting_started). Инструкции в интернете, которые ведут
в «Setup → API access», описывают консоль позапрошлой версии.

1. **Включить API.** https://console.cloud.google.com/apis/library/androidpublisher.googleapis.com
   → выбрать проект → **Enable**. Подойдёт любой проект (привязки к аккаунту разработчика больше
   нет), но API должен быть включён именно в том, которому будет принадлежать сервисный аккаунт —
   такой порядок в документации.

   **Лучше создать отдельный, например `dg-play-ci`.** Не ради прав — ролей в Cloud этот аккаунт
   не получит вообще и внутри своего проекта не сможет ничего, — а ради порядка: ключ от него
   единственный секрет в GitHub, в своём проекте он изолирован от Firebase, через который работает
   вход на сайте, и перевыпуск ключа не трогает ничего чужого. В чужом проекте сервисный аккаунт
   останется в IAM навсегда, и через год никто не вспомнит, что это. У самого приложения Firebase
   нет: `google-services.json` в репозитории отсутствует, плагин не применяется.
2. **Создать сервисный аккаунт.** https://console.cloud.google.com/iam-admin/serviceaccounts
   → **Create service account** → имя любое (`play-ci`) → **шаг с ролями Cloud пропустить**, права
   выдаются не здесь → создать. Затем открыть аккаунт → вкладка **Keys** → **Add key → Create new
   key → JSON**; файл скачается. Email аккаунта — вида `play-ci@<проект>.iam.gserviceaccount.com`.
3. **Выдать права в Play.**
   https://play.google.com/console/u/3/developers/5361675220359422085/users-and-permissions
   («Пользователи и разрешения»; `5361675220359422085` — id аккаунта разработчика, он же в адресной
   строке консоли, `u/3` — номер гугл-аккаунта в браузере, может отличаться)
   → «Пригласить пользователя» → этот email → в правах приложения выбрать `gift.dhamma.twa` →
   право **«Загружать приложения в тестовые каналы»** (Release apps to testing tracks).
   Больше ничего не давать: этого хватает для тестовых каналов (закрытое тестирование, alpha) и не
   хватает, чтобы выкатить что-то читателям.
4. **Секрет в каждом репозитории**, где нужна загрузка:
   - https://github.com/dhammagift/dg-apps/settings/secrets/actions
   - https://github.com/dhammagift/dg-twa/settings/secrets/actions
   - https://github.com/dhammagift/notApp/settings/secrets/actions

   **New repository secret** → имя `PLAY_SERVICE_ACCOUNT_JSON`, значение — **содержимое
   JSON-файла целиком**. Один и тот же файл во все три: сервисный аккаунт один, права у него на
   все три приложения.

   Общего секрета на несколько репозиториев тут быть не может: `dhammagift` — **личный аккаунт**
   (`GET /users/dhammagift` → `"type": "User"`), а секреты уровня организации бывают только у
   организаций. Поэтому три раза одно и то же — это не лень, это единственный вариант.

Правило Play «первую сборку загрузите вручную» нас не касается: пакет `gift.dhamma.twa` в консоли
уже есть, он заменил листинг TWA.

## Как отправлять

**Руками:** Actions → **Build App** → Run workflow → в списке **release** выбрать приложение и магазин
(`dg`, `dg-ios`, `dg-both`, `dict`, `dict-ios`, `uposatha`, `uposatha-ios`). Только из `main` и только с
сайтом `https://dhamma.gift` (иначе прогон падает в первом же джобе `plan`); выкладка ждёт проверок
своего приложения и не идёт, если они красные.
**Тегом:** один тег — одно приложение в оба магазина: `dg-v*` (или просто `v*`) — Dhamma.Gift, `dict-v*` —
словарь, `upo-v*` — Uposatha. Тег — это релиз, для теста его не ставят.
**Уже собранное:** `play-upload.yml` / `ios-upload.yml` с id прогона — только если тот прогон зелёный,
из `main` или тега, с боевым сайтом и с пройденной проверкой этого приложения.

Обычный пуш в ветку ничего не запускает, а ручной ран с `release: none` (по умолчанию) **никуда ничего
не отправляет** — ни в Play, ни в TestFlight. Раньше любой ручной ран уходил в App Store Connect, и это чинилось дважды, с обеих
сторон; правило владельца (20.09.2026): ручной ран не релизит.

## Куда именно приезжает

**Закрытое тестирование (alpha)** — у всех трёх приложений. Не production и не открытое тестирование,
и это осознанно:

- доезжает до устройства за минуты;
- видят только тестировщики закрытой группы владельца (Dhamma.Gift раньше уходил в открытое
  тестирование, beta; владелец остановил это 08.10.2026 — до открытых тестировщиков доехали гонки и
  регрессии; словарь и Uposatha переехали сюда с internal 04.10.2026);
- на продакшен всё равно нужен **promote** в Play Console — то есть автоматическая загрузка
  физически не может выкатить что-то читателям сама.

Повышение alpha → production остаётся ручным решением владельца. Это ровно та часть, которую никто не
просил автоматизировать.

## Что уезжает

Артефакт `dg-app-full-aab-release-<номер сборки>` (словарь — `dg-dict-aab-release-…`, Uposatha —
`dg-uposatha-aab-release-…`) из той же сборки — не пересборка. То есть в Play уезжают ровно те байты,
против которых прогнались проверки и которые лежат в артефактах рана.

`versionCode` — **свой номер у каждого приложения**, не номер рана (владелец, 11.10.2026: «у каждого
свой отдельный»). Его считает джоба `plan` (`.github/scripts/build_numbers.py`):
`max(build_floor из version.properties приложения, самый большой код этого пакета в Play, самая большая
сборка этого bundle id в TestFlight) + 1`. Номер растёт только от загрузок этого приложения, ниже
того, что уже есть в магазине, не бывает; тестовые сборки подряд получают один и тот же номер (ставится
поверх — Android не даёт ставить только меньший). Тот же номер — `CURRENT_PROJECT_VERSION` у iOS-сборки
этого приложения в том же ране. Номера всех трёх — в сводке рана и в `build-info.json`.

`applicationId` = `gift.dhamma.twa` (Dhamma.Gift), подпись — релизный ключ из секретов
(`ANDROID_KEYSTORE_*`). Если ключа нет, сборка не соберёт AAB, и загружать будет нечего — это видно в
сводке.

## Соседние репозитории

Владелец (20.09.2026) выдал сервисному аккаунту права на все свои приложения и просил настроить
то же самое для остальных — **после** того, как схема подтвердится здесь. Что есть на деле:

| Репозиторий | `applicationId` | Что сейчас | Что делать |
|---|---|---|---|
| `dg-apps` | `gift.dhamma.twa` (AAB), `gift.dhamma.mobile` (тестовый APK); `gift.dhamma.pali`; `gift.dhamma.uposatha` | `android-release`, `dict-release`, `uposatha-release` → `play-release.yml` | работает |
| `notApp` | `gift.dhamma.noapp` | только GitHub-релиз | перенести джобу один в один, поменяв `packageName` |
| `dg-twa` | `gift.dhamma.twa` | только GitHub-релиз | **не настраивать** |

Почему `dg-twa` — «не настраивать»: он объявляет тот же пакет, который теперь шлёт `dg-apps`
(приложение заменило листинг TWA). Два репозитория, способные залить один пакет в один трек, —
это грабли: чей `versionCode` выиграл, выяснится уже в консоли.

`otrn`, `dictPlugin`, `ddg-ui` Android-приложений не содержат — `applicationId` в них нет.
Если в консоли есть третье приложение, надо сперва выяснить, где оно собирается.

## Если что-то пошло не так

| Сообщение | Причина |
|---|---|
| `Missing repository secret: PLAY_SERVICE_ACCOUNT_JSON` | секрет не задан — см. шаг 4 |
| `The caller does not have permission` | сервисный аккаунт не приглашён в консоль или ему не выдано право на это приложение (шаг 3) |
| `Version code N has already been used` | этот номер уже в Play: обычно «Re-run failed jobs» после загрузки, которая прошла (`plan` при этом не перезапускается и номер старый). «Re-run all jobs» или новый ран перечитают Play и возьмут следующий |
| `APK specifies a version code that has already been used` | то же самое |
| `dg: play not read (...)` в `plan` | этот ран загружает в Play, а Play не ответил — номер нельзя сверить, ран остановлен сразу, а не через час на загрузке |
